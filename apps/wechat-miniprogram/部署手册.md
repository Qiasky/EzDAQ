## 3. 验证设备数据链路

在浏览器打开 [腾讯云开发控制台](https://tcb.cloud.tencent.com/dev)，使用「小程序公众号 / 微信公众平台」登录，选择与小程序相同的云环境。在「HTTP 网关 → 域名及路由」中添加路由：默认域名，访问路径 `/device-report`，关联资源类型「云函数」，资源实例 `deviceReport`，路由启用。路径透传和网关身份认证保持关闭；设备上报由云函数校验 HMAC 签名。只给 `deviceReport` 添加这条路由。

保存后，完整接口地址为 `https://默认域名/device-report`。将它提供给采集网关或用于模拟器（Python 标准库，无需额外安装依赖）：

```powershell
python scripts/mock_device.py --url "复制的 deviceReport HTTP 地址" --abnormal
```

模拟器仅用于开发环境，使用工程内的测试设备密钥。真实网关需要对齐设备编号与密钥，并按 `deviceReport` 的 HMAC 协议上报。工业协议在网关转换，小程序不直接轮询 Modbus / OPC UA 设备。

此处才需要一个新的地址：**deviceReport 的 HTTP 访问地址**，不是新 AppID，也不需要小程序前端接口域名。查看云数据库设备 `metrics` / `lastReportTime`，以及 `alarms` 新记录，确认「网关 → 云函数 → 小程序」链路。

本次开发环境已验证的上报地址为：

```text
https://cloud1-d3g4tp02la7e35e26-1500215617.ap-shanghai.app.tcloudbase.com/device-report
```

停止上报超过 90 秒后，设备总览按当前规则显示离线。模拟器目前只上报 `DEV001`～`DEV003`；台账另外 2 台设备没有模拟上报，保持离线。演示期间需要持续展示在线状态，可指定轮数连续上报，例如每 35 秒上报一次，共 10 轮：

### 韩感 LHG8950 家庭温湿度真实接入

接入链路：传感器 → 家中采集电脑（TCP/IP 读取）→ 当前 HTTPS 上报接口 → 微信云开发 → 小程序。传感器与采集电脑需要网络互通，采集电脑需要能访问当前云端上报地址。

用户提供的 LabVIEW 程序及补充参数已落实到 `scripts/lhg8950.config.example.json`：

| 参数 | 当前值及来源 |
| --- | --- |
| TCP 地址 | 已通过直连设备的 ARP 与 MAC 确认；地址保存在本地配置，公共示例留空 |
| TCP 端口 | 10050，用户提供 |
| 发送报文 | `3A30 3030 3435 3030 3030 3030 3841 340D 0A`，用户提供 |
| ASCII 表示 | `:000450000008A4` 后接真实 CRLF，共 17 字节 |
| TCP 超时 | 60000 ms，LabVIEW 截图 |
| 发送后等待 | 10000 ms，用户提供 |
| 响应长度 | 27 字节，LabVIEW 截图 |
| 响应地址 | 此次新设备实测 `0x1B`，本地 `responseAddress` 为十进制 27；公共默认值为空，沿用查询地址 |
| 温度位置 | 以 0 起算的偏移 11，取 4 个 ASCII 十六进制字符 |
| 正温度换算 | `(((高字节 & 0x07) * 256) + 低字节) * 0.0625`，按截图的「假」分支 |
| 湿度位置及换算 | 偏移 15，取 4 个 ASCII 十六进制字符，转整数后除以 10 |
| 无效湿度处理 | 此次实测持续 `FFFF`；本地 `invalidHumidityValues` 为 `[65535]`，保留有效温度并标记湿度无效；公共默认列表为空 |
| 采集周期 | 35000 ms，配合云端 30 秒节流、90 秒离线规则 |

发送帧的冒号、ASCII 十六进制、CRLF 和 LRC 符合 [Modbus ASCII 帧规则](https://www.modbus.org/file/secure/modbusoverserial.pdf)。采集器通过普通 TCP 套接字发送用户提供的原始帧，不添加 MBAP 头。实测返回 `:1B040850662181FFFF00245F` 后接 CRLF，LRC 有效；按提供的温度算法得到 24.0625℃。接收帧检查设备地址、CRLF、功能码、长度和 LRC，TCP 分包自动拼接。读取失败、校验失败或负温分支未确认时，不上传本轮数据。只有配置中明确列出的无效湿度原始值允许跳过，其他异常仍报错。

温度有效而湿度无效时，上报 `metrics: {temp: 实测温度}` 和 `metricQuality: {humidity: 'invalid'}`。云端使用 [字段 set 更新指令](https://docs.cloudbase.net/api-reference/webv1/database)替换最新监控点与质量标记，避免保留过期湿度；小程序湿度卡片显示「无效 / 采样无效，请检查探头」。收到有效湿度后清除质量标记，恢复数值显示。

1. 给传感器供电，并接入采集电脑可访问的网络。此次新设备先直接接电脑有线网口，通过抓取该标签 MAC 的 ARP 确认静态地址，配置电脑网段后完成 TCP 读取；随后按用户要求改为家庭路由器网段，并接回路由器 LAN 口。新地址的 MAC、配置读回和真实上报均已验证，TCP 10050 与串口参数保持原值。设备、本机地址及 MAC 保存在本地配置和 `.local/lantronix`，不进入交付包。其他设备可先用下方 Lantronix 官方工具发现地址。
2. 在小程序工程目录执行以下命令生成独立设备密钥和本地配置：

   ```powershell
   python scripts/lhg8950_gateway.py --init
   ```

   得到 `scripts/lhg8950.config.local.json` 与 `scripts/lhg8950.device.local.json`。此次配置已生成，无需重复初始化。在云开发控制台「数据库 → devices → 添加记录」粘贴设备文件的完整 JSON，建立 `HOME-TH-001` 台账；先确认不存在同编号记录。初始指标为空、时间为 0，直到真实上报成功才显示在线。
3. 将配置文件的 `host` 改为实际 IP。先执行只读测试，查看温度、湿度及原始接收报文：

   ```powershell
   python scripts/lhg8950_gateway.py --read-only
   ```

4. 完成下述云函数更新后，执行一次云端上报；在小程序编译后返回设备总览下拉刷新，搜索 `HOME-TH-001` 或「家庭温湿度」：

   ```powershell
   python scripts/lhg8950_gateway.py
   ```

   验证通过后持续采集：

   ```powershell
   python scripts/lhg8950_gateway.py --watch
   ```

   每轮重新建立 TCP 连接，断线后下一轮重新连接，Ctrl+C 停止。电脑上的采集程序须保持运行，设备状态才会持续更新。

负温度的 LabVIEW「真」分支不在截图中，当前 `negativeMode` 为 `unconfirmed`，遇到该标记会报错并保留原始帧。需补充分支后确认算法；配置中的 `signed12` 仅供已确认算法时使用。设备的密钥配置留在本地，交付压缩包只包含公共示例。

当前源码已补齐湿度保存、质量标记与显示，新环境需要在微信开发者工具中对 `cloudfunctions/deviceReport`、`deviceList`、`deviceDetail` 分别右键，选择「上传并部署：云端安装依赖」，然后编译小程序。2026-10-04 用户已完成三个设备云函数部署和 `HOME-TH-001` 台账添加，实际 24.25℃ 上报返回云端保存成功、状态 `normal`。后台每 35 秒持续采集，连续两轮真实上报成功；用户确认小程序已显示实际温度与湿度无效，链路验证完成。

本次持续采集进程在电脑后台运行，进程编号和输出、错误日志位置保存在 `.local/lantronix/gateway-process.local.json`。电脑须保持开机、网线连接且有互联网；电脑重启后重新运行上面的 `--watch` 命令。没有配置开机自启。停止本次后台进程前，先核对该文件的进程编号仍对应 `lhg8950_gateway.py --watch`，再在任务管理器结束该进程；前台启动的采集使用 Ctrl+C 停止。

#### 用 XPort 官方程序查找模块

Lantronix [官方支持页](https://ltrxdev.atlassian.net/wiki/spaces/LTRXTS/pages/106070471/Latest+version+of+DeviceInstaller)提供免安装的 `dsearch.exe`，使用 DeviceInstaller 搜索广播。工程已提供包装命令，首次从官方 HTTPS 地址下载并核对 SHA256，然后只查询设备：

```powershell
cd D:\Project\2026\EzDAQ\apps\wechat-miniprogram
npm.cmd run discover:xport -- --interface 192.168.31.122
```

`--interface` 是本机连接传感器网络的网卡 IPv4 地址。电脑接上有线网络后，用 `ipconfig` 查看并替换，不要选择 VMware 网卡。工具和原始查询日志保存在 `.local/lantronix`，不纳入 Git 或交付压缩包。

已知模块标签 MAC 时，在本地采集配置增加 `expectedMac`，搜索程序自动按它匹配；也可追加 `--mac 模块标签MAC`。该字段只用于发现目标身份，不代表已经找到 IP 或读到测量数据。若无发现结果，可在路由器「有线设备 / DHCP 客户端」中按完整 MAC 查找，获取地址后再验证读取。

此前 WLAN 与直连网卡查询中，官方工具只列出本机 IP、空设备 ID、全零 MAC，包装命令会过滤这类无效结果。此次通过设备标签 MAC 对应的 ARP 报文确认静态地址并完成 TCP 读取；官方发现服务没有有效回复不等于设备不可通信。其他设备搜索无响应时，可先确认有线网络与标签 MAC，再检查静态网段。

需要图形界面时，下载 [官方 DeviceInstaller 安装包](https://ts.lantronix.com/ftp/DeviceInstaller/Lantronix/4.4/4.4.0.7/Installers/Download_Web/DeviceInstaller-4407-Web.zip)。安装后在 `Tools → Options` 选择正确网卡，点 `Search`，查看 `Hardware Address` 与 `IP Address`。[官方操作手册](https://www.lantronix.com/wp-content/uploads/pdf/DeviceInstaller_UG.pdf)说明其他网段或未分配 IP 的设备会以红色显示。发现后先读取当前配置，核对 Channel 1 的 TCP 本地端口是否为 10050；串口参数须沿用 8950 原有配置，尚无依据指定新的波特率。

此次改址通过 Lantronix 官方 UDP 配置服务完成，先按 MAC 核对并读取、备份原始配置，再修改 IP 和对应网关；新地址读回确认除网络参数外原始配置一致。二进制配置可能包含管理密码，全部保存在 `.local/lantronix`，不打印或进入交付包。
