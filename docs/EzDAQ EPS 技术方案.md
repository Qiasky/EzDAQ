# EzDAQ EPS 技术方案

## 1. 目标与原则

本方案服务于 EzDAQ EPS MVP：集中监控环境、动力、安保与基础 IT 设备；提供实时状态、告警处置、通知、趋势和权限管理。

技术设计遵循以下原则：

- **平台优先**：以中心化 Web 平台为核心，满足多站点、多角色和远程访问。
- **采集独立**：现场采集与业务平台解耦，避免桌面客户端退出影响设备数据与告警。
- **逐步演进**：MVP 采用模块化单体，而非一开始拆分大量微服务。
- **多端复用**：Web、Windows 上位机与移动端尽量复用领域模型、接口契约和视觉规范。
- **可靠优先**：采集、告警和通知均要具备重连、缓存、重试和审计能力。

## 2. 总体架构

```text
┌─────────────────────────────────────────────────────────────┐
│ 使用端                                                       │
│ Web 管理端（Vue）│ Windows 上位机（Electron）│ App/小程序    │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTPS / WebSocket
┌───────────────────────────▼─────────────────────────────────┐
│ EzDAQ 中心平台（Java / Spring Boot 模块化单体）              │
│ 身份权限 │ 站点设备 │ 实时状态 │ 告警规则 │ 通知 │ 报表     │
└───────┬────────────────┬───────────────────────┬────────────┘
        │                │                       │
        │ PostgreSQL     │ Redis                 │ MQTT
        │ + TimescaleDB  │ 缓存/短期状态         │
┌───────▼────────────────▼───────────────────────▼────────────┐
│ 现场采集网关（Go，Windows Service / Linux systemd）          │
│ 协议适配 │ 本地缓存 │ 断线重连 │ 设备心跳 │ 安全上报       │
└───────────────────────────┬─────────────────────────────────┘
                            │ Modbus TCP / TCP-IP
                    传感器、UPS、配电、门禁、IT 设备
```

## 3. 技术栈选型

| 层级 | 推荐技术 | 选型说明 |
| --- | --- | --- |
| Web 管理端 | Vue 3、TypeScript、Vite、Element Plus、ECharts | 适合配置、表格、告警和大屏类企业界面；ECharts 用于趋势、仪表盘和统计图。 |
| Windows 上位机 | Electron + Vue 3 | 复用 Web UI，并补充全屏值守、开机自启、托盘、告警音和本地文件导出能力。 |
| App / 微信小程序 | uni-app + Vue 3 + TypeScript | 先覆盖告警、设备状态、趋势与现场确认；尽量共享前端领域逻辑。 |
| 中心后台 | Java 21、Spring Boot、Spring Security、MyBatis 或 JPA | 适合权限、审计、规则、通知和报表等企业业务能力；MVP 采用模块化单体。 |
| 现场网关 | Go | 适合常驻运行、并发 TCP 连接、断线重连和交付为单一可执行文件。 |
| 关系与时序数据 | PostgreSQL + TimescaleDB | 统一保存配置、告警、审计与监控点历史；按时间分区、压缩和聚合。 |
| 缓存 | Redis | 保存登录会话、热点实时状态、短时去重锁和限流计数。 |
| 消息链路 | MQTT Broker（如 EMQX） | 网关稳定上报数据和心跳；中心平台按主题消费。 |
| 实时推送 | WebSocket | 将设备状态和新告警推送至浏览器、Electron 和移动端。 |
| 文件与运维 | MinIO/S3 兼容存储、Docker Compose、Nginx | 保存导出报表及附件；适合小型客户私有化部署。 |

## 4. 各端职责

### 4.1 Web 管理端

Web 是完整管理入口，包含站点、设备、监控点、阈值、通知策略、用户权限、告警历史与报表。它通过 REST API 获取配置和历史数据，通过 WebSocket 接收实时状态和新告警。

### 4.2 Windows 上位机

Windows 上位机使用 Electron 承载同一套 Vue 页面，不直接负责设备采集。它适用于客户值班室：支持全屏大屏、托盘驻留、开机启动、告警声音、网络断开提示和本地 CSV/PDF 导出。

Electron 的本地能力必须只通过预加载脚本暴露有限 API；保持 `contextIsolation` 和渲染进程沙箱开启，禁止在渲染页面直接启用 Node.js 权限。

### 4.3 App 与微信小程序

移动端以“看状态、收告警、做确认”为目标，首期不放入复杂的设备建模、阈值和权限配置。建议页面包括首页概览、待处理告警、设备详情、趋势、个人通知设置。

### 4.4 现场采集网关

网关部署在客户现场网络内，负责数据源适配、协议轮询与数据标准化。网关以"数据源适配器"为单位管理接入通道，MVP 内置四类适配器：

| 适配器 | 接入对象 | 实现要点 |
| --- | --- | --- |
| TCP/IP | 主动上报的服务器/终端（如第三方平台推送、私有协议设备） | 客户端建连或监听端口；心跳与断线重连；按分隔符/帧格式解析。 |
| Modbus TCP | 标准 Modbus TCP 设备与网关 | 使用现成 Modbus 客户端库；按从站号与寄存器映射轮询。 |
| VISA | 本地 GPIB/USB/串口/TCPIP 仪器 | 通过 VISA 驱动库（如厂商提供的 visa32/IVI 运行时）打开会话，执行 SCPI 读写。 |
| 厂商 DLL | 第三方驱动 DLL 的设备 | 加载 DLL 并用 CGO/`syscall` 调用厂商导出函数（打开、读取、关闭），句柄生命周期由适配器管理。 |

网关将标准化后的数据、质量码、设备心跳发送到 MQTT；网络中断时写入本地轻量缓存，网络恢复后按时间顺序补传。

DLL/VISA 适配器运行在网关所在主机，受网关服务（Windows Service / Linux systemd）统一托管与重启；动态库与版本号记录在数据源配置中，加载失败时该数据源标记为"配置错误"而非静默忽略。

网关应以 Windows Service 或 Linux systemd 服务运行，支持配置文件/远程配置、日志滚动、自动重启和版本升级。MVP 不将视频流、复杂私有协议或电话语音放入网关范围。

## 5. 核心数据链路

```text
设备读数
  → 数据源适配器（TCP / Modbus TCP / VISA / 厂商 DLL）
  → 采集网关校验与标准化
  → MQTT 数据主题
  → 中心平台数据接入模块
  → 当前状态写 Redis，历史采样写 PostgreSQL/TimescaleDB
  → 告警规则模块判断产生、升级或恢复
  → 告警、通知记录与操作日志入库
  → WebSocket 推送 + 邮件/短信/微信/飞书/企业微信通知
```

建议统一一条采样消息的最小字段：`gatewayId`、`siteId`、`deviceId`、`pointId`、`value`、`unit`、`quality`、`collectedAt`、`reportedAt`。服务端以 `gatewayId + pointId + collectedAt` 做幂等保护，防止网关补传导致重复数据。

## 6. 后台模块划分

MVP 保持一个后端部署单元，但在代码层明确模块边界：

- **identity**：用户、角色、站点数据权限、登录和令牌。
- **asset**：站点、机房、**数据源**、设备、监控点与协议配置。
- **ingestion**：MQTT 消费、数据校验、设备心跳、当前状态与数据源在线状态。
- **alarm**：阈值规则、持续时间、告警状态机、合并、恢复和升级。
- **notification**：邮件、短信、微信、飞书、企业微信适配与重试。
- **history**：监控趋势、聚合查询、CSV 导出与保留策略。
- **audit**：配置变更与告警处置操作日志。

当设备量和站点数明显增长时，可以优先将 `ingestion` 和 `notification` 拆为独立进程；其余模块不必过早拆分。

## 7. 数据与容量策略

- 当前值优先写 Redis，并同步持久化到 PostgreSQL，首页查询不直接扫描历史采样表。
- 采样历史按时间分区；高频点可保存原始数据，较早数据以 5 分钟/1 小时聚合数据查询。
- MVP 默认原始采样保留 90 天，告警与审计保留至少 1 年；均应做成可配置策略。
- 历史趋势接口应限制单次查询时间跨度与返回点数，前端优先展示聚合结果。
- 以设计目标 5,000 个监控点估算时，采集周期应按设备重要性分级，避免所有点均按秒级入库。

## 8. 部署建议

小型客户首期使用私有化单机/双机部署：

```text
客户服务器或虚拟机
├─ Nginx：HTTPS、静态前端、反向代理
├─ EzDAQ 中心后台：Java 服务
├─ MQTT Broker
├─ PostgreSQL + TimescaleDB
├─ Redis
└─ Docker Compose：统一安装、启动和升级

客户现场网络
└─ 一个或多个采集网关：连接设备并安全上报中心
```

首期无需 Kubernetes。生产环境至少需设置数据库每日备份、应用日志滚动、基础监控、磁盘容量告警和网关离线告警。

## 9. 安全设计

- 全部客户端与中心平台使用 HTTPS/WSS；网关与 MQTT 使用 TLS 和独立凭据。
- 用户采用基于角色与站点范围的权限控制；所有告警确认、关闭及配置修改写入审计日志。
- 网关只允许访问所需设备网段和平台地址；不开放不必要入站端口。
- 通知渠道的 Token、Webhook 和数据库密码使用加密配置或密钥管理，不写入前端与日志。
- Electron 不加载不受信任远程页面，不向渲染进程暴露任意文件系统或命令执行能力。

## 10. 实施顺序

| 阶段 | 交付重点 |
| --- | --- |
| P0：技术验证 | 一个 Go 网关接入温湿度与 UPS；数据进入 MQTT、后台入库并在 Web 显示。 |
| P1：MVP 平台 | 用户权限、站点设备、实时总览、告警状态机、企业微信/飞书/邮件通知、趋势和 CSV 导出。 |
| P2：多端交付 | Electron 上位机、uni-app 小程序/移动端、值班提醒与离线提示。 |
| P3：规模优化 | 数据聚合、网关批量管理、告警升级、报表订阅和更多协议。 |

## 11. 当前明确不做

- 不在 MVP 中建设完整微服务平台、Kubernetes 或流式大数据集群。
- 不让 Electron 或移动端直接连接并轮询现场设备。
- 不在首期实现视频实时预览、录像、AI 预测维护和复杂工单流程。
- 不因追求代码复用而强行让 Web、Electron、App、小程序共用全部 UI；优先共用接口、类型和设计规范。
